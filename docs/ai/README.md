# AI Agent Documentation

Supporting material for AI-assisted work in this repository. It does not define
the working rules — [AGENTS.md](../../AGENTS.md) does, and it wins on every
conflict.

## How the pieces fit

| Layer | Lives in | Loaded | Purpose |
| --- | --- | --- | --- |
| Repository rules | [AGENTS.md](../../AGENTS.md) | Always | Commands, architecture, engineering policy, testing policy, skill routing |
| Skills | [`.agents/skills/`](../../.agents/skills/README.md) | On demand, per task | Narrow, verifiable task guidance (`golang-*`, `go-project-layout`, `backend-spec`, `project-conventions`) |
| Role agents | [`prompts/`](prompts/) | When you invoke one | Scoped subagent definitions surfaced to Claude Code through `.claude/agents/` |
| Review template | [`templates/review.md`](templates/review.md) | When you write a review | Structure for the records kept in [`docs/reviews/`](../reviews/README.md) |

Skills are the primary routing mechanism. AGENTS.md maps a task type to the
narrowest skill that covers it and to the command that verifies the change; use
that table first. Role agents are an optional way to keep a long piece of work
inside one responsibility — they do not replace the skills, and a skill still
applies inside whichever agent is running.

```
ai/
├── README.md        # This overview
├── prompts/         # Role agent definitions (symlinked into .claude/agents/)
│   ├── documentation.md
│   ├── planning.md
│   ├── review.md
│   └── development.md
└── templates/
    └── review.md    # Code review record template
```

`.claude/agents/` holds relative symlinks to the prompts, and `.claude/skills/`
holds relative symlinks into `.agents/skills/`. Both are regenerated by
`make agents-setup` and validated by `make skills-check`. Never copy a prompt
or skill into `.claude/`; edit the file here.

## Role agents

| Agent | Owns | Does not | Writes to |
| --- | --- | --- | --- |
| [Documentation](prompts/documentation.md) | Feature specs (`backend-spec`), READMEs, these prompts | Application code, plans, reviews | Co-located `<package>.spec.md`, `docs/flows/`, `docs/`, package READMEs |
| [Planning](prompts/planning.md) | Turning an approved spec into an ordered, package-scoped plan with risks and verification | Application code, requirements gathering | The plan returned for approval |
| [Review](prompts/review.md) | Analysis of changes against AGENTS.md policy | Modifying code, writing plans | `docs/reviews/` |
| [Development](prompts/development.md) | Implementation, fixes, refactors, and the tests that protect them | Specs, its own review documents | Source packages |

The natural chain is Documentation → Planning → Development → Review, with
Review looping back to Development for fixes. A handoff carries what was
completed and the state of the working tree, open issues or decisions, the
acceptance criteria the next step must satisfy, and the verification commands
already run with their results.

### Which agent

| Task | Agent | Start with skill |
| --- | --- | --- |
| Feature specification | Documentation | `backend-spec` |
| README or guide update | Documentation | — |
| Authoring or editing a skill | Documentation | `agent-skills` |
| Implementation plan | Planning | `go-project-layout` |
| Code quality or security review | Review | the skill matching the changed area, `golang-security` |
| Feature implementation, bug fix, package move | Development | the AGENTS.md routing table |

## Plan then execute

Each role agent supports a plan step and an execution step. Plan first — and
get the approach approved before editing — when the change spans multiple
files or packages, needs architectural or placement decisions, touches
unfamiliar territory, or carries high risk (security, persistence,
concurrency, breaking changes). Execute directly for mechanical, decision-free
changes or when following a plan that was already approved. When unsure, plan.

A unit of work is one package stage: a complete, testable change scoped to one
package that compiles, passes the required test tiers, keeps generated code
current (`make generate-check`), and updates package documentation for new or
materially changed contracts. Plans are sequenced by package stage with a
commit point at each boundary.

Model selection is a client-side concern and deliberately not specified here.

## Quality gates and failure reporting

Every agent's work is subject to the gates in AGENTS.md, enforced by
`make check` (plus `make race` for concurrency or lifecycle changes and
`make test-integration` for database or generated-contract changes). An agent
that cannot meet them reports the command, its output, and what remains
unfinished, then stops — it does not lower the bar, skip verification, or narrow
the requested scope on its own.
