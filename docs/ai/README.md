# AI Agent Documentation

Supporting material for AI-assisted work in this repository. It does not define
the working rules — [AGENTS.md](../../AGENTS.md) does, and it wins on every
conflict.

## How the pieces fit

| Layer | Lives in | Loaded | Purpose |
| --- | --- | --- | --- |
| Repository rules | [AGENTS.md](../../AGENTS.md) | Always | Commands, architecture, engineering policy, testing policy, skill routing |
| Skills | [`.agents/skills/`](../../.agents/skills/README.md) | On demand, per task | Narrow, verifiable task guidance (`golang-*`, `go-project-layout`, `backend-spec`, `project-conventions`) |
| Role agents | [`prompts/`](prompts/) | When you invoke one | Scoped subagent definitions surfaced to Claude Code through `.claude/agents/` |
| Templates | [`templates/`](templates/) | When you write a document | Feature specs, implementation plans, review reports, new agent prompts |

Skills are the primary routing mechanism. AGENTS.md maps a task type to the
narrowest skill that covers it and to the command that verifies the change; use
that table first. The role agents below are an optional way to keep a long
piece of work inside one scope — they do not replace the skills.

## Role agents

| Agent | Scope | Writes to |
| --- | --- | --- |
| [Documentation](prompts/documentation.md) | Specs, READMEs, prompts, templates | `docs/features/`, `docs/ai/` |
| [Planning](prompts/planning.md) | Task breakdown and risk assessment | `docs/plans/` |
| [Review](prompts/review.md) | Code quality analysis | `docs/reviews/` |
| [Development](prompts/development.md) | Implementation and fixes | Source packages |

`.claude/agents/` holds relative symlinks to these files, and `.claude/skills/`
holds relative symlinks into `.agents/skills/`. Both are regenerated by
`make agents-setup` and validated by `make skills-check`. Never copy a prompt
or skill into `.claude/`; edit the file here.

## Plan then execute

Each role agent supports a plan step and an execution step. Plan first for
anything non-trivial — multiple files, architectural decisions, unfamiliar
territory, or high-risk changes — and get the approach approved before editing.
Go straight to execution only for mechanical changes or when following a plan
that was already approved.

Model selection is a client-side concern and deliberately not specified here.
