# Code Reviews

This directory contains point-in-time code review records for the Go project.
Current architecture guidance lives in
[`docs/architecture/`](../architecture/README.md); historical findings may cite
paths or behavior that no longer exist.

## Purpose

The reviews directory serves as a central location for:

- **Review outputs**: Completed code reviews generated by AI agents
- **Review templates**: Structured formats for consistent code review documentation
- **Review process documentation**: Guidelines and workflows for code reviews
- **Historical review records**: Archive of completed reviews for reference

## How Code Reviews Work

### Review Modes

This project supports two primary code review modes:

#### 1. Package Review Mode
Review entire packages as cohesive units:
```bash
# Review the auth package
internal/auth

# Review the config package  
internal/platform/config

# Review the storage package
internal/platform/database
```

**Usage**: Provide a specific package path to focus the review on that package's design and implementation.

#### 2. Git Changes Mode (Default)
Review only changed files using git diff:
```bash
# Review all changed Go files (no package specified)
# Agent automatically detects changed files using:
# - git diff --name-only master...HEAD (branch changes)
# - git diff --name-only (unstaged changes)
# - git diff --name-only --cached (staged changes)
```

**Usage**: Don't specify a package path, and the review agent will automatically detect and review changed .go files.

### Review Agents

The project uses AI-powered code review agents configured via `docs/ai/prompts/review.md` that:

- Analyze code changes for bugs, security vulnerabilities, and performance issues
- Ensure adherence to Go conventions and project standards
- Provide constructive, specific, and actionable feedback
- Verify test coverage and quality for changed code
- Check for breaking changes and backward compatibility

## Review Process

### Standard Review Workflow

1. **Code Changes**: Developer makes changes to Go code
2. **Review Request**: Request code review (either package-specific or git changes mode)
3. **Automated Analysis**: AI agent analyzes code using established criteria
4. **Review Output**: Structured review document is generated
5. **Developer Action**: Address feedback and iterate as needed
6. **Review Archive**: Completed review is stored in this directory

## Templates and Tools

### Review Template
Use the structured template at `docs/ai/templates/review.md` to create consistent review documentation:

```bash
# Copy template for new review
cp docs/ai/templates/review.md docs/reviews/[feature-name]-review.md
```

The template provides:
- **Review structure**: Standard sections (Summary, Critical/Major/Minor Issues, Positive Notes)
- **Review criteria checklist**: Code Quality, Go-Specific Issues, Project Standards
- **Validation checklist**: Ensures review quality and completeness
- **Placeholder guidance**: Clear instructions for consistent completion

Refer to the template for detailed review criteria and structure requirements.

### AI Review Agent
The code review agent is configured in `docs/ai/prompts/review.md` and provides:
- Automated code analysis
- Standards enforcement
- Consistent feedback formatting
- Integration with project development workflow

## Review Quality Standards

### Feedback Guidelines
- **Be specific**: Reference exact lines and provide examples
- **Be constructive**: Suggest solutions, not just problems
- **Be educational**: Explain the "why" behind recommendations
- **Be respectful**: Focus on code, not the person
- **Prioritize**: Distinguish between must-fix and nice-to-have issues

### Review Checklist
- [ ] Code builds and tests pass
- [ ] No critical security vulnerabilities
- [ ] Proper error handling throughout
- [ ] Adequate test coverage for changes
- [ ] Go conventions followed (gofmt, golint, go vet)
- [ ] Documentation updated where needed
- [ ] No breaking changes without version bump
- [ ] Performance implications considered
- [ ] Concurrency safety verified
- [ ] Clean git history and commit messages

## Common Review Scenarios

### New Feature Review
1. Verify feature completeness against requirements
2. Check test coverage and edge cases
3. Validate error handling and input validation
4. Review performance implications
5. Ensure documentation is updated

### Bug Fix Review  
1. Verify the fix addresses the root cause
2. Check for regression test coverage
3. Ensure no new issues are introduced
4. Validate error handling improvements
5. Review related code that might be affected

### Refactoring Review
1. Verify backward compatibility is maintained
2. Check that behavior is preserved
3. Validate test coverage is maintained
4. Ensure code clarity is improved
5. Review performance impact

## Integration with Development

Code reviews integrate with the overall development workflow:

- **Pre-commit**: Run reviews on staged changes
- **Pull requests**: Include review outputs in PR descriptions
- **Feature development**: Package reviews for major features
- **Refactoring**: Architecture reviews for structural changes
- **Security**: Focused security reviews for sensitive changes

## Best Practices

### For Developers
1. **Request reviews early**: Get feedback during development, not just at the end
2. **Provide context**: Include background and requirements with review requests
3. **Address feedback**: Take review comments seriously and respond appropriately
4. **Learn from reviews**: Use feedback to improve future code quality

### For Reviewers
1. **Focus on important issues**: Prioritize security, correctness, and maintainability
2. **Provide examples**: Show how to fix issues, not just what's wrong
3. **Be consistent**: Apply standards uniformly across all reviews
4. **Stay current**: Keep up with Go best practices and project evolution
